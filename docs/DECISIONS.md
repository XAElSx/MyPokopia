# Decisions

Format: what, why, alternative.

- **Batch instruction supersedes two CLAUDE.md working rules for this run.** "Stop and show me before the next feature" and "ask before new file structure" are overridden by the 7-phase instruction. The rules stay in CLAUDE.md for later work.
- **Deleted `data/pokemon.js`** (the 5 placeholder Pokémon with made-up specialties). Nothing loads it since the real database arrived; keeping it would conflict with "never invent game data".
- **Progress shape is designed once, in Phase 1.** One localStorage key `pokopia.collection` = `{version, updatedAt, entries, habitats, houses, town}`. `entries` by Pokémon id, `habitats` by slug, `houses` by house id, `town` by area. Why: sync sends one file and later phases only add keys. Alternative: one key per feature (rejected: sync would need several files and the "differs" check gets harder).
- **`migrate()` only adds missing sections and bumps the version, it never prunes ids.** Old progress keyed by sample ids like `bulbasaur` stays in `entries`, unused but not deleted.
- **Sync mirrors MyDex** (github.com/XAElSx/MyDex, `js/sync.js`): private Gist, found by file name `pokopia-progress.json`, token in localStorage under its own key `pokopia.token`, gist id under `pokopia.gistId`. Token is never part of the progress object, so Export and the Gist can't contain it.
  - **Conflict flow differs from MyDex on purpose.** MyDex merges per record; the brief for Pokopia says "show both timestamps and let me choose". Rule: remember the timestamp both sides last agreed on (`pokopia.lastSync`). Only local changed since then -> push. Only the Gist changed -> pull (after saving a backup copy in `pokopia.backup`). Both changed, or first connect with different data -> show both timestamps, I choose. Alternative: always ask when different (rejected: asks after every edit).
- **Cross-page links use hash links** (`habitats.html#tallgrass`, `index.html#main-001-bulbasaur`): same behaviour on file:// and GitHub Pages.
- **One global per data type** (`POKOPIA_DB`, `POKOPIA_HABITATS`, ...). `build_js.py` takes the global name as an argument so a second data file can't overwrite the first.
- **`build.py` takes targets** (`python tools/build.py habitats`). Default behaviour for the Pokémon target is unchanged. The raw cache `../pokopia-raw` doesn't exist on this machine, so I don't re-run the Pokémon pipeline.
- **Test tooling lives outside the repo** (scratchpad): headless Chrome driven over CDP with a fresh profile, never the real one.
- **Habitat areas = union of the Location lists of the Pokémon on the habitat page.** The habitat pages have no area field of their own. 194 habitats are in all six base areas, 39 also in Bubbly Basin, the rest are limited (e.g. Palette Town + Cloud Island). Alternative: take areas from `pokopia-pokemon.json` (rejected: same source, and the habitat page is the one being scraped).
- **Habitat requirements without an item link keep `itemSlug: null`** (Water, Tree, Lighting, Seat, ...). They are generic objects, not items with a page, so they can't link to a recipe. Not an error.
- **8 habitats list different Pokémon on Serebii's habitat page and on the Pokémon pages** (e.g. Charizard at Tall Grass). The guide uses the Pokémon pages (`pokopia-pokemon.json`) since they carry rarity, time and weather; the differences are in the verify list.
- **`itemSlug` for Phase 4 is captured now** (from the item link href) so a requirement can link to its recipe without matching on names.
- **Recipes: items.shtml supplies "where to get the materials".** Serebii's crafting page lists materials but not where they come from; the items page does (1710 items, with location lines). Materials link to their own recipe when one exists, otherwise show the first locations. Alternative: scrape all 1710 item pages (rejected: the index tables already hold the same fields, one request instead of 1710).
- **9 recipes are flagged in the verify list** (Serebii typos such as "Linestone", "Iron ignot", empty material cells, one recipe listed in two categories). They are kept as scraped; nothing was corrected by hand.
- **Pairings score: same `idealHabitat` is required for a pair to count; each shared favorite is one point; house score = sum over all member pairs.** Flavor is not counted (the brief says "shared favorites"). A house with different ideal habitats still scores but is flagged "mixed ideal habitats". Max 4 members, enforced by hiding the add control. Alternative: weight flavors or give a 0-100 rating (rejected: simplest rule first).
- **Houses are stored as `houses[id] = {name, members[]}`** with generated ids (`house-…`), so Phase 7 can place a house by id.
- **Building blocks live as a "Blocks" mode on the pairings page**, not a separate page: the data is favorite -> items, and favorites already appear there (a Pokémon's favorites link to their items; a house card links the favorites everyone shares). Alternative: its own `blocks.html` (rejected: another page for 43 rows).
- **Item grouping uses the recipes item list for the category** (Blocks, Furniture, ...) because Serebii's favorite pages leave the category blank for many items; "Blocks" is listed first and selected by default when a favorite has any.
- **Town grid is 12 x 12 squares per area**, stored as `town[area] = {w, h, cells}` so a different size can come later without breaking saved layouts. Seven areas: the six base areas plus Bubbly Basin. Why 12: 12 squares fit a 390 px phone at about 28 px each and the whole grid fits on a PC screen. Alternative: a freely scrolling large grid (rejected: not "simple").
- **One thing per square; the same house or habitat can be placed in several squares** (the legend shows ×N). A square whose house was deleted in Pairings turns red ("missing") instead of vanishing, so no layout data is lost silently.
- **Town reads Pairings houses and guide habitats by id/slug at render time**, so renaming a house or marking a habitat built shows up in the planner without any copying.
- **Habitat fixes (second pass).** `tools/habitats.py` now reads every row of Pokémon on a habitat page (it only read the first row of 4, so 8 habitats were missing Pokémon; the 8 "list differs" flags are gone and the cross-check reports 0 differences). Corrections to Serebii are coded in `AMOUNT_FIXES`, `BLANK_FROM_PT` and `MISSING_REQUIREMENTS` in that file, each checked against Pocket Tactics and flagged in the verify list: Illuminated tall grass Lighting 10 -> 1, Hydrated flower bed + Water x2, six blank amounts set to 1. Seabed tall grass (Basin tall grass) stays blank because Pocket Tactics doesn't list it.
- **"High-up location" is moved to `conditions`** (new field on each habitat, shown as "Placement" in the guide) instead of being dropped. It was in 8 habitats, not 5: the five "Elevated ..." ones plus Berry-feast Campsite, Waterside dinghy and Picturesque photo cutout board (all three had amount 1). I treated all 8 the same since it is the same placement condition; say if those three should keep it as a requirement.
- **Item spelling unified (25 occurrences across 21 names):** most common spelling wins; ties go to the variant with more lower-case letters; a name never starts with a lower-case letter ("seashore flowers" became "Seashore flowers" although the lower-case form was 2 of 3).
